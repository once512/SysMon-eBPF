## 实机对照与功能检查

开发内核为 `6.12.0-211.61.1.el10_2.x86_64`，BTF/BPF LSM 可用。使用现有 GNU++17、clang/libbpf，不修改内核参数；`kernel.io_uring_disabled=2`，本轮未验证 io_uring。

修改前，以预先打开 FD 的同一个进程设置诱饵的 user xattr、POSIX ACL 和文件标志，三个操作均成功，随后修改其他文件也成功，且没有拒绝事件。这是本轮修补的实际缺口。

新增专题使用 root 私有复制的请求程序及已有 FD，验证：

- xattr/ACL 的设置与删除、SETFLAGS、FSSETXATTR、FICLONE/FICLONERANGE，逐项独立 canary 响应；仅 setattr 授权不能获得新权限。
- 错误执行对象、硬链接、租期、vault 读写会话与身份对象优先级；同一执行 inode 不能通过显式授予自身 all 修改自身 ACL、capabilities 或文件标志。
- pwritev、fallocate 打洞、copy_file_range、FIDEDUPERANGE 目标、传统 Linux AIO O_DIRECT 写、splice、sendfile 的拒绝与独立诱饵触发。
- 真正 i386 进程的 compat ioctl，包含已有 FD、授权范围、vault、响应和解除；无需额外 32 位 libc。
- 未触发时允许已验证的只读查询；未知命令只拒绝、不创建响应。活动响应优先于 writer/vault，对普通文件的全部 ioctl 拒绝。

## 已发现问题与处理

1. 第一轮完整回归在自保护 `--run-for 1` 的 5 秒总预算上超时，当时还在并行运行解析器模糊测试。未修改该上限；单独复测通过。随后三次独立分阶段采集显示启动约 0.119–0.130 秒，总耗时 3.601–4.016 秒，大部分剩余时间位于运行结束/卸载阶段。并行负载是超时发生时的环境，尚不将其断言为唯一原因。
2. 完整回归查出 writer 容量专题仍将 all 的预期矩阵写成八个槽。修正为十三槽，保留第63位规则与其余目标不获授权的检查；原先显式八项操作列表的 255 掩码仍按原范围验证。
3. 第一次元数据短时持续测试严格比对发现每轮多一条未知 ioctl：Python 读取普通文件时的 `TCGETS` 探测。新增只读查询白名单并验证保留 ENOTTY；不通过调大预期计数接受噪声。修正后15秒受控段完成90轮/3004命令，2524条拒绝、186次响应、2158次后续限制，原始审计3044条与独立公式一致，212项运行代码/构建摘要前后一致，控制器FD4/4。
4. 最终检查修正了无 libc 的 i386 启动夹具对编译函数的栈对齐；后续兼容路径与持续段使用重建产物。
5. 原生完整回归61项通过，最后一项pidfd权限审计背压用例正常退出码0，但耗时3.234秒，超过原3秒全程预算；该轮整体仍记失败。独立探针对25个链接串行卸载耗时2.413秒，20次慢close累计2.406秒；4/8线程分别2.715/2.627秒，未采用并发卸载。背压和退出专题现独立要求权限组500ms内释放、完整退出5秒内完成，输出仍堵住；这是明确的验收预算调整，原3秒指标未达标。

## 结论边界

以上证明指定开发内核和已测文件系统路径下的对象保护及限时响应。SETVERSION 仅按命令保守分类，没有本机成功修改基线；未知 ioctl 收紧可能影响尚未列入白名单的工具。真实/虚拟文件系统之间的覆盖不能互相代替。

本轮没有实现 FUSE 虚拟诱饵、可信恶意意图判据、已建立映射撤销、在途 I/O 取消、已有子进程隔离、跨重启持久防护、最终用户认证或加密恢复。生产防护承诺仍需部署基线和相应验收。
